## 2. 初始问题（用户提出）

**Q0-1：格式应与流行引擎的预制体/资产集合结构相似或易转换。**
→ 结论：✓ 通过对齐"节点树 + 组件 + 资产引用 + 实例带差异"这一业界收敛点达成；真正的分叉在 override 模型、身份/引用、根语义三处。参考系选择：结构语义看 glTF/USD/Unity，**版本与分发看 npm/OCI**——因为游戏引擎在版本维度集体交白卷（它们假设资产与场景共同演进，而 Nook 假设创作者发版、构建者钉版）。

**Q0-2：内存结构高效，空间与 IO 速度平衡。**
→ 结论：✓ 拆解后发现"效率"的真实落点不在编辑器本地存档（小规模，JSON 足够），而在三处：① 商城→编辑器下载（CAS 去重，升版只下变化 blob）；② 编辑器永不下载 full 负载；③ 烘焙产物的运行时（属世界格式范畴，未讨论）。L3 内存布局（SoA/TypedArray）整体 ⏸ 延期，判定为"太远，先定上层"。

**Q0-3（用户的困惑）：飞书文档中的约束、概念、问题"没有感觉"。**
→ 诊断：文档只展开了语义层（transform 组合 A/B/C），而用户的直觉在找其他层。"预制体格式"不是一个决策而是三层，各层决策正交，不必同时拍板。

## 3. 产品层决策

**Q1（助手问）：创作者在哪 authoring？**

- 用户答：在各引擎（Unity/Unreal）创作，经平台 Nook SDK 导入生态（LOD 上传商城、商城下载到编辑器）。格式同时存在于商城预览、资产存储、编辑器实时预览、后端烘焙原材料。**主要属交换格式，但也有创作格式在**。
- 推论：✓ "交换格式 vs 创作格式"拆开——编辑器内存表示自由，序列化走交换格式；"人类可读"对预制体包基本可放弃（对世界存档再议）。

**Q2（助手问）：构建者能改什么？**

- 用户答：只能改 transform 和创作者暴露的参数。参数类型未定但必含数值（int/float）、物体（Nook 预制体）、材质、贴图。
- 推论：✓ 无需 Unity 式自由 override（见 §4-D）。

**Q3（助手问）：预制体更新后实例怎么办？**

- 用户答：**钉住旧版，用户自行选择何时升级**。
- 推论：✓ 参考系从游戏引擎转向包管理器：不可变 `id@version`、多版本共存、lockfile 心智、CAS 去重。

**Q4（⚑5，助手问）：嵌套预制体在哪创作？**

- 用户答：**创作者导出时自行选择**——被嵌套的可以成为/对应 Nook 预制体（存在依赖），或整合进父预制体。（"对应商店现有预制体"这一点用户标注"话题可能很宽"。）
- 定型：✓ **静态链接 vs 动态链接**心智（USD flatten、链接器、Unity unpack 同款）；选动态链接 → 包间依赖 → 发布顺序约束（被依赖方先发布或按依赖序同发）→ 包需要自己的依赖声明。

**Q5（⚑2，助手问）：商城预览能调参吗？**

- 用户答：不确定但**倾向于可以**。
- 推论：✓ 硬约束——proxy + 参数声明必须自足可渲染；R7 后进一步定型为"proxy 绑定缺失则该参数预览不生效（INFO/WARNING）"（见 §7-R7）。

**Q6（⚑4，助手问）：参数值烘焙时固化还是运行时动态？**

- 用户答：取决于编辑器用户，确实复杂，**向后讨论**。本轮目标是"尽可能确定稳固的标准，完成 PoC 后再推进"。
- 状态：⏸ 延期。格式暂不区分烘焙期/运行时参数。

**Q7（助手问）：世界文件里除预制体实例还有散装内容吗？**

- 用户答：不确定，很可能完成整个流程后才考虑。⏸
- 附带确认：世界格式有自身约束但未想清楚，**等预制体定义稳固后再讨论**。

**Q8（助手问）：当前仓库契约（CANONICAL_FORMAT.md）的地位？**

- 用户答：✓ 确认是旧 scratch，不符合实际产品思路，**可以更换**。

**Q9（流程暴露，助手插旗，未深聊）**：

- ⚑1 SDK 本地预览/模拟器（创作者上传前能否预览"Nook 化"结果）——待定。
- ⚑6 版本下架/废弃策略（钉住该版本的世界怎么办）——待定。

**Q10（R8 新增，评审触发）：自定义着色器与运行时可编程性的定位？**

## 4. 语义层决策

**D. override 模型**

- 选项：自由 override（Unity 式，任意属性差异表，propertyPath 键控）vs 声明式参数（创作者声明旋钮，实例只赋值）。
- 选择：✓ **声明式参数**。用户最初直觉"差异集/override 可能还需要"，经概念辨析后确认不需要——构建者权限范围（transform+暴露参数）内没有自由 override 的用例。
- 理由：定形数据 `{paramId: value}`；校验 trivial；UI 自动生成；跨引擎天然；跳过 Unity 预制体系统最难的部分。
- 关键澄清：**引用型参数（prefab/材质/贴图）的值会给世界引入新依赖** → 依赖闭包收集必须遍历参数值。

**E. 锚点（用户技术意见 1："更换版本时参数独立性与更新问题，必须存在可选择干预的迁移过程，参数绑定和 override 可能需要锚点"）**

- 结论：✓ 锚点拆两种，稳定性要求不同：
  - **paramId** = 迁移锚点，跨版本稳定，面向创作者/SDK（实例值能跟着升版的唯一依靠）。
  - **nodeId** = 绑定锚点，只需版本内稳定，面向 SDK；只有被参数绑定的节点才需要。
- 收益：版本内绑定可随便重构，只要 paramId 保住，实例值即可迁移。

**F. 根语义（飞书文档 A/B/C 之争）**

- 选项：A（identity 根）、B（双变换叠加，文档推荐）、C（锚点，无根节点）。
- 结论：✓ **按 B 存储 + 组合语义独立**。交换格式第一原则是限域无损捕获：glb 逻辑根保留创作者根变换原值；placement 与 root 如何组合是规范里的一行规则（叠加，identity root 时退化为 A）。
- 理由：把"格式决策"降级为"语义规则 + SDK 校验"。冷知识佐证：Unity 实例化实为**覆盖**根 transform（存为 modification），USD/glTF 才是**叠加**；Nook 取叠加语义。
- proxy/full 组合结果一致性 = SDK 导出校验职责。
- R7 补充（评审 4.4）：✓ 逻辑根约束定型——恰好一个逻辑根；源单根打标记（`extras.nook.packageRoot` + 保留 nodeId `nook.root`），多根合成 identity 包裹根；组合公式 `world = ancestors × placement × storedPackageRoot`。

## 5. 参数类型系统（R4 确认，R7 修正）

- ✓ 类型清单 v1：int / float / bool / string（用户补）/ enum / color / vec2 / vec3 / prefabRef。`textureRef`、`materialRef` R7 后定为**保留类型（类型名注册，v1 不支持）**。curve、gradient 挂起 ⏸。
- 绑定基数：✓ 由原作者配置，1..n；可以驱动 transform（壁灯"凸出距离"用例——R7 后由保留根 nodeId `nook.root` 统一寻址）。
- ⏸ UI 生成规则：是很大的讨论，需专门一张表，**不是现在**。
- ✓ prefabRef 参数可限定接受的预制体类型/分类；materialRef 是独立资产还是内联属性组 ⏸ 未定（保留类型期间缓议）。
- ✓ 兼容规则表（见标准文档 §10）——升版审查 UI 的判定依据；R7 修正：`renamedParams` → `parameterReplacements`（例外通道），displayName 变更不产生迁移条目。

## 6. 身份分配（线程 4）

**Q：Unity .meta GUID "运行效率低下缓慢"的既有评价是否成立？（用户转述并猜测"可能因为它直接暴露给用户"）**

- 辨析：✓ 误归因。GUID 查找 O(1)，Unity 运行时根本不用 GUID；慢来自导入/刷新全库扫描与 Library 重建。.meta 真正的病是**运维脆弱性**（用户要管的第二个文件：忘提交、资源管理器复制撞车、合并冲突、编辑器外移动丢失）——用户的猜测更接近真相。
- 对 Nook 的推论：身份只在创作期/导出期/注册表使用，运行期用解析好的直接引用——"运行效率"不在讨论维度内。

**Q：身份策略选型？**

- 选项对照：

| 策略 | 先例 | 跨版本稳定 | 创作者负担 | 翻车模式 |
| --- | --- | --- | --- | --- |
| sidecar 文件持久 | Unity .meta | 高 | 管理/提交 sidecar | 丢失、复制撞车、合并冲突 |
| 组件内嵌持久 | VRChat PipelineManager | 高 | 装 SDK、不删组件 | 复制资产→ID 撞车 |
| 路径派生 | Godot / USD | 低（改名即断） | 零 | 重命名/重构全断 |
| 内容哈希派生 | git / CAS | 无 | 零 | 任何编辑换身份 |
| 导出时对账匹配 | git rename 检测 / React reconciliation | 中（启发式） | 审查 UI | 相似节点误配 |

- 选择：✓ **不选单一策略，按稳定性需求分配**（用户确认）：
  - blob → 内容哈希；prefabId → NookAuthoring 组件（首次启用分配）；paramId → 组件内 SDK 分配、永不暴露；nodeId → 混合制（绑定表持久 + 导出重解析 + 对账兜底 + 警告 UI）。
- 关键解锁：**绝大多数节点不需要跨版本身份**——需要锚点的只有"旋钮的作用目标"，是很小的集合。
- 翻车对策：Ctrl+D 撞车 → 导出检测 + 询问新建/覆盖；组件被删 → 对账提议恢复（⏸ PoC 后增强）。
- 副产品：商城下载的预制体自带身份组件 → 嵌套引用直接读到 `id@version`，无需人工映射。
- ⚑ 未定：paramId 形态（倾向 UUID + 自由 displayName + 可选语义 slug；R7 的 parameterReplacements 定性进一步支持 UUID 取向）；对账相似度算法；Unreal 侧载体。

## 7. 包解剖（线程 2）与 R7 评审处置

### 7.1 R6 原结论

**子问题 1：结构信息放哪？**

- 选项：α manifest 存结构、glb 只当几何负载（双真相源）vs β glb 存结构、manifest 只存语义。

### 7.3 前向兼容定稿（R8，用户确认）

评审四层分级 + `requires` 建议方向正确，但有两个坑需填：**requires 与正文重复会漂移**；"不支持配置"与"直接拒绝"之间缺桥。定稿为**三层消费者行为 + 注册表治理**：

```
① 未知可选元数据 / payload 槽 → 保留+忽略
② requires 中未知能力 → 默认拒绝（NOOK-UNSUPPORTED-CAPABILITY）；
   角色化降级可选（强制检查/仅渲染 proxy），禁止配置、禁止再发布
③ 任何情况往返保留（round-trip preservation，评审未提但 interchange 必需；
   先例反面对照 Unity、正面对照 USD）
```

- `requires` 由 SDK 机械生成、验证器强制 `⊇ 实际使用`（照搬 glTF extensionsUsed/Required 心智并加漏报=ERROR）；排序去重（影响哈希）。
- 能力注册表独立版本化（`nook.parameter/color@1` 等）→ 新增参数类型**不动 manifest 主版本**；演进矩阵：新增→注册表条目；值域不兼容→能力 @v+1；结构破坏→spec 主版本。
- `x.*` 实验前缀保留，商城包禁用。
- 为什么现在定：存量包出现前定义 rejection 语义成本近零，事后补是破坏性变更；v1 真实场景是灰度期编辑器版本滞后。

### 7.4 "运行时一致性"重命名（R8，用户确认）

- 旧架构下 parity 成立：两个解释器读**同一份**内嵌表示，"等价解释"良定义。
- 新架构下失效：消费方读**不同表示**（proxy/full/烘焙产物），渲染**本来就不该相同**（LOD 是设计使然）；parity 会误导实现与验收。
- 重命名为**表示层语义一致性**，四条不变量：参数语义一致（绑定声明范围内）、组合数学一致、身份/版本语义一致、诊断语义一致。明确不要求像素等价。
- 可测性反而变好：无需渲染的夹具断言 → 本地验证 PoC 的核心手段。
- OpenSpec 能力相应改名 `prefab-runtime-parity` → `prefab-semantic-consistency`。

### 7.5 OpenSpec 边界重划（R8，用户确认）

- `prefab-contract-foundation` 收缩为**包契约基础 + 本地验证/检查 PoC**：manifest 模式、身份与不可变版本、payload 角色、可移植 profile、根组合、参数声明与绑定、嵌套引用、依赖闭包、验证诊断、.nookpkg、最小世界引用边界、夹具。
- 范围外：云 API/存储实现、商城发布、认证权益、生产后端、完整世界格式、升级 UI、完整 SDK、烘焙实现、VRChat 发布、运行时动态参数。
- 必须写入旧路径处置立场（Q11）。
