## 1. Purpose and scope

This format supports the storage and transfer of prefabs across the following pipeline:

```
Creator (Unity/Unreal + Nook SDK) ──export──▶ Prefab package ──upload──▶ Cloud mall (registry + CAS)
                                                                              │
        ┌──────────────────────────┬──────────────────────────────────────────┤
        ▼                          ▼                                          ▼
   Mall preview (proxy)      Browser editor (proxy live preview)        Backend bake (full as input)
```

- This format is **primarily an interchange format**: generated by the SDK and consumed by the SDK, services, and the editor; it is not meant to be hand-written.
- The editor's in-memory working representation is not constrained by this format (whatever is convenient); only on-disk/on-wire serialization follows this format.
- Scope is limited to the **prefab package**. The world/scene file is referenced only as "instance record requirements" (§9); its own format will be discussed separately.

## 2. Design principles

1. **Interchange-first**: creators author with native engine tools; this format is the SDK's export product and the object consumed by all parties.
2. **Scoped lossless**: export must faithfully preserve creator data that falls within the Portable Prefab Profile (§4); content outside the profile **must not be silently dropped** — the SDK must emit explicit diagnostics at export time.
3. **Immutable versions + pinned instances**: published versions are immutable; placed instances in a world pin their version, and upgrading is an explicit builder action.
4. **Content addressing (CAS)**: payloads are addressed by content hash, deduplicated across versions and across prefabs; upgrades download only changed blobs.
5. **Engine-agnostic**: relies only on industry standards (JSON, glTF); engine-specific concepts are mapped by the SDK at export time.
6. **Declared parameters, no freeform overrides**: instances may only modify the placement transform and creator-declared parameters.
7. **Round-trip preservation**: consumers must preserve unrecognized fields and values verbatim when re-serializing (see §13).

## 3. Roles and lifecycle

| Stage | Participant | Relationship to this format |
| --- | --- | --- |
| ① Authoring | Creator (engine + SDK) | Native engine construction; SDK provides the parameter-declaration UI (NookAuthoring component) |
| ② Parameter declaration | Creator | SDK assigns paramIds and records binding targets |
| ③ Export/packaging | SDK | Validates (profile compliance, bindings resolvable, proxy/full consistency, requires completeness) → produces package |
| ④ Upload | SDK → mall | Option A (draft): whole-archive upload; server unpacks into CAS (§14) |
| ⑤ Storage/preview | Mall | Registry records `id@version`; proxy renders the mall preview standalone (parameter adjustment intended, tentatively confirmed) |
| ⑥ Acquisition | Builder (editor) | Downloads manifest + proxy into local cache; world file records the dependency (version pinned) |
| ⑦ Placement/configuration | Builder | Produces instance records; parameter types drive UI generation (UI rules TBD) |
| ⑧ Upgrade/migration | Builder | Auto-carry + review panel (§10); downloads only changed blobs |
| ⑨ Bake | Backend | Resolves the dependency closure, fetches full payloads, replaces proxies, produces the runtime world |

## 4. Nook Portable Prefab Profile

Only a **whitelisted subset** of a native engine prefab may enter a Nook package. "Lossless" holds only relative to this subset, not relative to the engine's full feature set.

```
Native engine prefab
      │  SDK export
      ▼
┌─────────────────────────────────────────┐
│ Nook Portable Prefab Profile v1         │
│  · Geometry (meshes / primitives)       │
│  · PBR materials (glTF metallic-        │
│    roughness + whitelisted official     │
│    material extensions)                 │
│  · Lights (KHR_lights_punctual)         │
│  · Nook semantic components (collider / │
│    pickable / avatar placeholder;       │
│    managed via the capability registry) │
│  · Transforms                           │
│  · Whitelisted parameter-target         │
│    properties (§7 path language)        │
└─────────────────────────────────────────┘
```

- **Out-of-profile content** (arbitrary scripts, custom shaders, engine-specific components, animation controllers, engine events, engine physics configuration, editor-only behaviors, arbitrary serialized objects): the SDK must emit explicit diagnostics at export time (WARNING or ERROR); silent dropping is forbidden.
- Profile content evolves incrementally through the capability registry (§13) without a manifest major-version bump.
- ⚑ **The long-term story for custom shaders and runtime programmability is a Lark-level product question, filed separately**; this draft makes no default decision on it.

## 5. Package logical model

A prefab package = **one manifest + several content-addressed blobs**.

```jsonc
// manifest.json
{
  "spec": "nook.prefab/1",            // manifest format version
  "id": "p_01J9Z...",                 // prefabId: SDK-assigned, stable across versions (§8)
  "version": "1.2.0",                 // creator-facing version (semver style)
  "meta": {
    "name": "Vintage Wall Lamp",
    "author": "...",
    "category": "furniture/light",
    "tags": []
  },
  "requires": [                       // capability declaration, see §13; mechanically
    "nook.component/collider@1",      // generated by the SDK from actual usage;
    "nook.parameter/color@1"          // sorted and deduplicated (part of canonicalization)
  ],
  "parameters": [ /* ParamDecl[], see §7 */ ],
  "dependencies": [                   // dynamically linked nested prefabs; pinned at publish
    { "kind": "prefab", "id": "p_01K4...", "version": "2.0.1", "digest": "sha256:6f1c..." }
  ],
  "payloads": {                       // typed slots, extensible
    "proxy": { "digest": "sha256:a1...", "size": 812344,  "mediaType": "model/gltf-binary" },
    "full":  { "digest": "sha256:b2...", "size": 52428800, "mediaType": "model/gltf-binary" }
    // Future slot examples: "thumbnail", "materialLib" — new slots do not change the format version
  },
  "migrationHints": {                 // optional, exceptional migration channel (§10)
    "parameterReplacements": { "oldParamId": "replacementParamId" }
  }
}
```

**Version identity and hashing rules**:

- `digest = sha256(JCS(manifest))` — JCS is the RFC 8785 JSON Canonicalization Scheme (sorted keys, no whitespace, normalized number serialization), ensuring independently implemented SDKs compute identical digests.
- The manifest does **not** contain its own digest; the `requires` array is **sorted and deduplicated** (JCS does not sort arrays, so sorting is part of canonicalization).
- Digest encoding: `sha256:<lowercase hex>` (OCI style). Blob digests are computed over raw bytes; no canonicalization needed.
- **Registry invariants**: each `(id, version)` may be published only once; republishing the same tuple with a different digest must be rejected; dependency digests participate in the manifest hash (recursive fingerprint); blob digest and size must be verified before consumption.

**Dependency pinning and collection**: in the creator workspace, dependencies may be declared as version ranges (e.g. `^2.x`, package.json mental model); at publish time the SDK resolves them to exact versions + digests in the manifest (lockfile mental model), so published packages are forever reproducible. **In-package dependency sources = nested-instance extensions (§6) + reference-typed parameter default values**; dependency-cycle detection is required at publish time.

## 6. Payloads and structural ownership (Option β)

**Structural information (the node tree) lives only in the glb; the manifest holds only semantics** — a single source of truth.

- **proxy (draft: glb)**: the LOD representation, standalone-renderable (v1 embeds textures; external URIs forbidden), serving the mall preview and the editor's live preview. The editor **never downloads full**.
- **full (draft: glb)**: bake input — high-poly meshes + full textures; flows only between creator → cloud → bake backend.
- **Node anchors**: glb nodes carry `extras.nook.nodeId`; parameter bindings reference these ids.
- **Logical root constraint**: every package has **exactly one logical root node**. Single-root source → mark it directly (`extras.nook.packageRoot = true`, reserved nodeId `nook.root`, addressable by parameter bindings — e.g. a wall lamp's "protrusion distance"); multi-root export → the SDK synthesizes an identity wrapper root and marks it the same way. The composition formula is unambiguous:

  ```
  effectiveRoot = worldAncestors × instancePlacement × storedPackageRoot
  ```

  (Composing semantics; degenerates naturally when storedPackageRoot is identity.)
- **Nested instance encoding**: a glb node carries the extension; the node's own transform is the placement, recursively consistent with top-level instance semantics:

  ```jsonc
  { "extras": { "nook": { "prefabInstance": {
      "kind": "prefab", "id": "p_01K4...", "version": "2.0.1",
      "digest": "sha256:...", "params": { "shadeColor": "#AA8844" }
  } } } }
  ```

  Separation of duties: the node extension answers "where is it instantiated, how is it placed, what are the parameter values"; `manifest.dependencies` answers "what must resolve, at which pinned version, with which integrity digest".
- **Semantic components**: Nook components such as collider / pickable / avatar placeholder live under node `extras.nook.components`; standard glTF viewers ignore them. Lights use the official `KHR_lights_punctual` extension; physics will align with draft KHR physics extensions in the future.
- **proxy/full consistency**: the two must produce consistent composed render results (within proxy precision constraints). This is an **SDK export-time validation duty**, not a format concern. proxy and full are generated by the SDK in a single export pass from one data source.

## 7. Parameter system (v1)

```jsonc
// ParamDecl
{
  "paramId": "...",            // migration anchor, stable across versions, SDK-assigned, not exposed to creators
  "displayName": "Primary color", // UI display name; freely changeable, produces no migration entry
  "type": "color",             // see type table
  "constraints": {},           // value domain (type-dependent)
  "default": "#FFD700",
  "bindings": [                // representation-scoped bindings; author-configured cardinality, 1..n; may target transforms
    { "representation": "full",
      "nodeId": "n_bulb",
      "propertyPath": "mesh.primitives[2].material.pbrMetallicRoughness.baseColorFactor",
      "required": true },
    { "representation": "proxy",
      "nodeId": "n_bulb_proxy",
      "propertyPath": "mesh.primitives[0].material.pbrMetallicRoughness.baseColorFactor",
      "required": false }
  ]
}
```

**Representation-scoped binding rules** (replaces the v0 single-path binding model):

- proxy and full are two independent glbs; a manually authored proxy may differ completely in hierarchy, material slots, and merging, so **the same path is not guaranteed to point at the same semantic property in both payloads**. Bindings must therefore be declared per representation role.
- A `full` binding must resolve, otherwise export fails with **ERROR**; a `proxy` binding may be absent (the parameter simply has no preview effect; export emits **INFO/WARNING** so the creator is informed). The `representation` enum is extensible.
- Tooling convention: **explicit format, ergonomic tooling** — the creator binds once against the source asset and the SDK dual-writes both entries in the common case; auto-generated proxies get auto-derived proxy bindings; manual proxies are confirmed by the creator via an SDK mapping UI.

**Path language (`nook.path/1`, whitelisted semantic paths)**:

- Root namespaces: `transform` (`translation` / `rotation` / `scale`, glTF naming), `mesh.primitives[...].material...`, `nook.components.*`.
- Segment syntax: dot-separated + `[i]` array indices + by-name segments (e.g. `material.named("BulbGlass")`) — by-name segments are the robust alternative when indices are fragile (primitive/material reordering); bindings must be revalidated at export time when indices shift.
- The **writable-property whitelist × parameter-type compatibility table** is a single artifact serving both validation and parameter UI generation; every target has an expected value type; escaping rules ship with the syntax definition.
- Extensions may register new paths (via the capability registry, §13). Fully arbitrary JSON paths are forbidden (they break validation, cross-engine mapping, security, and type checking).

**Type table (v1)**:

| Type | Status | Domain/constraints | Notes |
| --- | --- | --- | --- |
| `int` / `float` | ✓ v1 | min / max / step | |
| `bool` | ✓ v1 | — | |
| `string` | ✓ v1 | maxLength? | |
| `enum` | ✓ v1 | options: [{value, label}] | |
| `color` | ✓ v1 | — | |
| `vec2` / `vec3` | ✓ v1 | per-component min/max? | |
| `prefabRef` | ✓ v1 | may constrain accepted prefab types/categories | reference type, enters dependency closure |
| `textureRef` | ⏸ reserved | format/size constraints? | not supported in v1; type name registered |
| `materialRef` | ⏸ reserved | ⚑ standalone material asset vs inline property group TBD | not supported in v1; type name registered |
| ~~curve / gradient~~ | suspended | — | revisit after PoC |

**Unified reference envelope**: reference-typed parameter values, the instance's prefabRef, and manifest dependency declarations share one shape:

```jsonc
{ "kind": "prefab", "id": "p_...", "version": "1.2.0", "digest": "sha256:..." }
// kind ∈ registry: "prefab" | "material" | "texture" | ...
```

Rules:

- **Reference-typed parameter values introduce new dependencies into a world**: dependency-closure collection must traverse instance parameter values, not just instance references; same inside packages (§5 dependency collection).
- An instance's parameter assignment = `{ paramId: value }` fixed-shape data; validation is trivial; UI can be generated from type + constraints (generation rules table TBD).
- Preview consumers apply only their own representation's bindings (see above); the bake backend applies all full bindings on full.

## 8. Identity allocation

| Identity | Strategy | Stability requirement | Carrier |
| --- | --- | --- | --- |
| blob | content hash (derived) | content is identity | CAS storage key |
| prefabId | component-embedded persistence | stable forever across versions and exports | NookAuthoring component on the root, assigned at first "enable Nook" |
| paramId | component-embedded persistence | stable across versions (migration anchor) | inside the NookAuthoring component, SDK-assigned at declaration, never exposed |
| nodeId | hybrid | only needed by binding-target nodes | binding table stored in the NookAuthoring component: {paramId → [binding targets]}; re-resolved at export, falling back to reconciliation matching, then to an export-time warning UI for re-pointing |

- The vast majority of nodes need no cross-version identity; they are serialized wholesale with each version's glb structure.
- **Failure modes and countermeasures**: duplicating a prefab asset collides prefabIds → detected at export, prompting "new prefab or overwrite", with a fresh ID assigned if new; a deleted NookAuthoring component → export reconciles against the published package and offers to restore identity (post-PoC enhancement).
- **Nested references land naturally**: prefabs downloaded from the mall carry their identity component in the creator's project, so a parent prefab referencing them reads `id@version` directly — no manual mapping.
- **Runtime-irrelevant**: these identities are used only at authoring/export/registry time; runtimes (bake output, editor preview) use direct references resolved at load.
- ⚑ Open: the concrete form of paramId (leaning toward machine UUID + free displayName + optional semantic slug — the parameterReplacements exceptional channel further supports the UUID orientation, see §10); the reconciliation similarity algorithm (PoC: exact matching + warn-on-break only); the Unreal-side NookAuthoring carrier (needs engineering validation).

## 9. Instance model (requirements for the world format)

The minimal record of one prefab instance in a world file:

```jsonc
{
  "prefabRef": { "kind": "prefab", "id": "p_01J9Z...", "version": "1.2.0", "digest": "sha256:..." },
  "transform": { /* placement, builder-editable */ },
  "params": { "paramId": "value" }   // whether to store only non-default values: TBD
}
```

- Instances **do not allow** freeform overrides; in-definition instances of nested prefabs (§6 extension) share this shape recursively.
- Multiple versions of the same prefabId may coexist in one world.
- The world format itself (loose content, lights, terrain, etc.) is out of scope here and will be discussed after the prefab definition stabilizes.

## 10. Versions and migration

- Published versions are **immutable**; instances pin versions; upgrades are explicitly triggered by the builder and **must include a user-intervenable migration process**.
- Upgrade flow: automatic paramId matching → diff review panel → atomic switch on confirmation → download only changed blobs.
- **displayName changes produce no migration entries** (renames are free); a new paramId means a new parameter identity.

| Change between versions | Handling of existing instance values |
| --- | --- |
| displayName / description changed | safe, carried directly |
| constraints narrowed | carried + clamped, flagged in the review panel |
| enum options added | safe |
| enum options removed/changed | automatic if the creator provides a mapping, otherwise manual selection is prompted |
| int ↔ float | automatic conversion |
| other type changes | not automatic → filled manually in the review panel; new default used if left empty |
| parameter removed | warning; ⚑ whether old values are kept as dead data (for rollback) — trimmable |
| parameter identity replacement (exceptional channel) | manifest `migrationHints.parameterReplacements` → carried automatically; only for accidentally regenerated IDs, replace/merge/split, and recovery from lost authoring metadata — **casual ID changes must not become the norm** |
| parameter added | creator default applied, listed for review |

- ⚑ Open: version delisting/deprecation policy (what happens to worlds pinned on a delisted version).

## 11. Representation-semantic consistency

(A rename and refinement of the `prefab-runtime-parity` concept in the OpenSpec proposal.)

Under the new architecture, consumers read **different representations** (proxy / full / baked output), and their render results are **not supposed to be identical** (LOD is by design). The representation-level equivalence implied by "parity" is neither the goal nor achievable. The invariants that must hold are:

1. **Parameter semantic consistency**: the same parameter value produces the same semantic effect within each representation's **declared binding scope** (paths differ; semantics match).
2. **Composition math consistency**: `ancestors × placement × storedPackageRoot` yields the same world transform in every consumer.
3. **Identity/version semantic consistency**: an instance refers to the same `id@version@digest` everywhere; migration rules behave identically.
4. **Diagnostic semantic consistency**: the same invalid document produces the same diagnostic codes across implementations.

Explicitly **not required**: pixel/render equivalence; identical internal data structures; proxy preview of parameters that declare no proxy binding.

Testability: fixture assertions that require no rendering (node existence, transform values, material values, component flags, diagnostic codes) — the core method of the local validation PoC.

## 12. Validation, diagnostics, and security

Packages are **untrusted interchange artifacts**. Validators must use battle-tested glTF parsing libraries (binary parsing surface), never home-grown parsers.

**Manifest checks**: supported spec major version; legal id/version (semver); all dependencies pinned with no duplicate tuples; no dependency cycles; unique paramIds; defaults satisfy constraints; bindings compatible with value types; `requires ⊇ actual usage`, sorted and deduplicated; no missing required capabilities.

**Archive and blob checks**: digest/size mismatch; missing or extra blobs; ZIP path traversal; duplicate archive paths; ZIP bombs and decompression limits; manifest size cap; node/primitive/texture count caps; no external URIs (v1); malformed glb; unsupported extensions; scripts or executable payloads.

**Severity policy**:

| Level | Meaning |
| --- | --- |
| ERROR | the package cannot be imported, published, or baked |
| WARNING | the package is valid, but preview or migration behavior is degraded |
| INFO | compatibility or optimization suggestion |

Stable, machine-readable **diagnostic codes are part of the contract** (e.g. `NOOK-UNSUPPORTED-CAPABILITY`), guaranteeing invariant 4 of §11.

## 13. Forward compatibility

**Three tiers of consumer behavior**:

```
① Unknown optional metadata / unknown optional payload slots
   → preserve + ignore (payload slots unless explicitly requested)
② An entry in requires that the consumer does not recognize
   (parameter types / components / path features)
   → reject by default: NOOK-UNSUPPORTED-CAPABILITY
   → role-scoped degradation is optional: inspection tools may force-open,
     preview may render proxy only; but configuring instances and
     republishing are forbidden (the precise definition of the
     "unsupported configuration" state)
③ Round-trip preservation in all cases
   → re-serialization must carry unknown fields and unknown-typed
     parameter values verbatim
```

**Capability registry and `requires` governance**:

- Namespaces: `nook.parameter/<type>@<v>`, `nook.component/<name>@<v>`, `nook.path@<v>`, etc.; each capability is **versioned independently**.
- `requires` is **mechanically generated** by the SDK from actual usage; validators enforce `requires ⊇ actual usage` — under-reporting is a package validation ERROR (drift eliminated by construction).
- An experimental prefix `x.*` is reserved; packages published to the mall must not carry experimental capabilities (registry governance policy).
- Capability support is **per-consumer**: during staged rollouts, an older editor opening a world with newer packages degrades cleanly instead of corrupting data.

**Evolution mechanism decision matrix**:

| Change | Mechanism |
| --- | --- |
| New parameter type / component / payload slot | new registry entry; spec version unchanged; old consumers degrade per ② |
| Incompatible change to a capability's value domain | capability version +1 (e.g. `color@2`) |
| Breaking change to the manifest structure itself | `nook.prefab` major version +1; higher majors are rejected (existing rule) |

## 14. Storage and transport

The canonical model is manifest + CAS blobs, with two losslessly interconvertible physical serializations:

**Wire form (OCI-style)**: the manifest is an API object; blobs are independently addressable objects.

```
Editor install / mall preview:  GET manifest → payloads.proxy.digest → GET blob (cached forever by digest)
Bake backend:                   GET manifest → full blob → recursively resolve the dependencies closure
Upgrade:                        GET new manifest → diff digests → download only changed blobs
```

**Archive form**: `.nookpkg` (zip) = **a single package + its own payloads**, for import/export/backup/single-package offline transfer; it is **not dependency-closure self-contained**.

```
wall-lamp_1.2.0.nookpkg
├── manifest.json
└── blobs/
    ├── sha256_a1...glb   (proxy)
    └── sha256_b2...glb   (full)
```

A future `.nookbundle` (root package + full transitive dependency closure) may be defined; for now only the distinction is registered, not the format.

**Upload (draft: Option A)**: the SDK uploads one `.nookpkg` archive; the server unpacks it into the CAS. The protocol is designed to be compatible with Option B (blob-by-blob push with digest-skip, OCI-push style); a future SDK upgrade changes no server semantics.

**Editor local cache**: a CAS store (digests as filenames) + an index (`id@version → manifest`), the pnpm-store mental model; offline editing is possible with a warm cache.
